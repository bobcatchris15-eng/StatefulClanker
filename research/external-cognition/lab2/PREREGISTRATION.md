# Lab 2 preregistration: opaque external state on a binary-chain task

**Registration status:** design-level preregistration, dated 2026-10-01. Freeze the implementation, generated inputs, assembled prompts, scoring code, and arm labels before launching any subject. Append a dated deviation log rather than changing this document after seeing subject outputs. The first campaign is exploratory and descriptive.

## Question and bounded claim

Can fresh model calls carry forward a compact, machine-checked frontier while solving a generated multi-stage task, and how does that compare with solving the complete task in a fresh call or carrying a record-form frontier? This tests the operational usefulness and failure modes of externalized intermediate state on one synthetic task family. It does not test a general reasoning benefit, establish a native capacity threshold, or demonstrate access to neural hidden states.

The state may be opaque to a person. The subject-facing observations in this campaign are explicit numeric vectors or records, not encoded bytes. The packed codec is a backing-store encoding. Opaque/base64-looking storage is not a learned latent representation and does not show that a model can reason over uninterpretable bytes. The experiment varies state presentation (vector versus records) and storage codec (packed versus JSON) as distinct factors; conclusions about either must follow the actual arm assignment and exposed prompt.

## Task and independent correctness

The task generator creates `N` stages. At stage `i`, choose bits `x_i,y_i` such that `(b_i + x_i + y_i) mod 2 == parity_i`, where `b_i` is the incoming boundary (`0` initially, then the previous stage's `y`). Add `wx_i*x_i + wy_i*y_i` to cumulative cost. The required final boundary is specified by the generated problem. Minimize total cost; ties use lexicographically smallest complete bit string. The exact frontier after a prefix retains the minimum-cost, lexicographically preferred witness for each feasible outgoing boundary. No boundary is charged twice.

An independent exhaustive enumerator for small fixtures and a separately implemented dynamic-programming oracle for larger fixtures score outputs. Before live use, cross-check the two methods on all registered small fixtures. The subject prompt must include task rules and its exact input but no oracle, scorer, hidden key, or precomputed next frontier. A checker can detect whether a proposal matches the task specification; it does not establish that the subject independently solved the task or that the state representation was cognitively meaningful.

## First campaign, fixed inputs, and arms

Use model `gpt-6-luna`, low reasoning effort, fresh subject context per call, and the tool's common procedural 20,000-character input ceiling if that remains the available setting. Record the actual route/settings and any unavailable sampler, token, or context statistics. The ceiling is procedural; it is not evidence of native incapacity.

1. **Complete-task calibration (six fresh calls):** one full-task attempt for each `(blocks, seed)` pair with blocks in `{2,4,8}` and seed in `{1101,1102}`. Ask for the exact optimal cost and complete bit string in the frozen JSON schema. No state artifact or transition checker feedback is supplied. Score exact cost and bits, schema validity, and independent feasibility/optimality. These six outcomes are a coarse task-family calibration snapshot only, not a reliable capacity curve or threshold estimate. In particular, successful full-task DP responses are direct evidence that these instances were solvable by the tested route, not proof of a general internal capacity.
2. **Four-stage vector chain (four fresh calls):** seed `1101`, four stages, one fresh subject per stage. Expose the exact local stage and prior accepted frontier as numeric vectors `[boundary,cost,bits]`; store the durable state using the packed codec. Each call proposes the next frontier. The transition checker accepts only the exact legal frontier. A rejected proposal leaves the committed state unchanged.
3. **Four-stage records chain (four fresh calls):** same generated four-stage problem and stage ordering, with frontier rows exposed as `{boundary,cost,bits}` records. Use JSON backing storage. This is a descriptive presentation-plus-codec comparison, not a clean storage-only contrast. Preserve identical task facts, order, checker, and response schema wherever possible.
4. **Input-update follow-up:** only if the vector chain completes all four stages, change zero-based stage 1's `wx` by `-2`, preserve the unchanged prefix, invalidate the affected suffix, and recompute stages 1 onward using fresh calls. Independently verify the preserved prefix, updated problem hash/version, each recomputed frontier, and final optimum against the updated full-task oracle. This tests dependency invalidation and recomputation mechanics, not reasoning generalization.

The six calibration calls are not substitutes for chain baselines: match additional fresh complete-task attempts to the number of chain calls (four per chain, plus update calls if feasible), preferably on the same generated problem with frozen prompt/schema. If matching is infeasible, record precisely which calls were made and the reason; do not describe the comparison as call-matched. Even matched call counts do not equate tokens, sampling, total computation, or the useful intermediate work embedded in a frontier. Report these resource gaps explicitly.

## Outcomes and decision rules

Report, per call and per chain: raw-output preservation/hash and byte length; response/schema validity; proposed-frontier exactness; checker acceptance; accepted-prefix length; rejection count; repair count; final exact optimum; number of calls; prompt/response characters and store bytes; and available token/resource data. Byte sizes are not token counts. Preserve rejected proposals and their diagnostics; never silently substitute an oracle state.

Primary transition endpoint: number of exact, independently oracle-matching proposed frontiers among attempted stage transitions, reported as numerator/denominator separately for vector and records chains. Also report accepted transitions and exact final optimum, since checker rejection and final solution accuracy are different endpoints. Primary calibration endpoint: exact full-task optimum rate at each of the three sizes, with both seeds shown individually; no pooled inferential test. A chain is complete only if every required stage proposal is exact and accepted and the final result equals the independent oracle.

After each rejected step, permit at most one fresh semantic-feedback repair for that step. Feedback may identify the failing rule/field and say the proposal failed exact validation, but must not reveal a corrected frontier, witness, cost, or oracle answer. Freeze repair wording before subjects. A repaired proposal is scored as a separate attempt; retain the original rejection and count both calls. No further retries. If rejection prevents the next legal state, downstream work may be stopped; if implementation sends a stale/rejected proposal onward for diagnostic purposes, mark it invalid and do not count downstream outputs as valid chain transitions.

Report outcomes descriptively. Do not claim statistical significance, a model population rate, general capacity, or state superiority from this small fixed campaign. A difference between arms is inconclusive as a representational or storage effect if call/resource exposure differs materially or if the compared arms jointly vary presentation and codec. A valid checker plus wrong subject proposals is evidence of checker detection on these proposals, not proof that validation causes reliable recovery.

## Failure, deviation, and stopping rules

- Invalid JSON/schema, infeasible assignments, wrong costs, nonminimal frontier rows, wrong tie witness, or incomplete/malformed final answer score as incorrect for the relevant endpoint. Preserve exact raw bytes.
- On a rejected patch, durable state must remain byte-for-byte/logically unchanged at the prior committed version; record receipt, state hash/version, and diagnostics. A storage/checker/runtime defect is an implementation failure, not a subject error. Pause live dispatch, preserve artifacts, fix and refreeze before launching new subjects; report any already-run subjects separately and never pool across versions without labeling the deviation.
- Corrupt payload, stale version/hash, wrong stage, or malformed patch must be rejected safely in pre-subject tests. If this invariant fails in a live run, stop that arm and report an infrastructure failure; do not improvise a state repair.
- Missing token/settings/resource telemetry is reported as unavailable. Do not infer equality from matching model name, character ceiling, call count, or byte count.
- No oracle fallback, hidden answer insertion, post hoc prompt editing, unlogged retry, or replacement of a rejected state is allowed. Any accidental exposure or prompt/runtime deviation is logged with affected calls; affected outcomes are excluded from the nominal arm table and shown separately.
- Stop an arm on persistent infrastructure malfunction, unsafe/corrupted state, or an inability to preserve raw inputs/outputs. Do not stop because subject performance is poor or favorable.

## Interpretation limits

The full-task calibration is not an independently established capacity threshold: it samples only six small generated instances, one route/settings, and a bounded task family, with no held-out reliability criterion or scaling curve. The task has a transparent dynamic-programming solution and may be easy for the subject. The chain also decomposes the task and gives explicit transition constraints; success could reflect the task format, extra sequential computation, or frontier content. The checker can solve/verify task-specific mechanics and makes acceptance stricter, but it cannot turn a correct output into evidence that the subject needed external state. The frontier carries answer-bearing prior search work. Even additional full-task attempts matched by call count would not match total compute absent token/sampling telemetry and a compute-matched baseline. Accordingly, report only observed exactness, transitions, costs, and mechanics for these fixtures; no claim that external cognition overcomes an internal limit or improves reasoning in general.
